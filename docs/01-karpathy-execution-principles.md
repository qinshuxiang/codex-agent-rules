# Codex 核心执行原则

本文件约束 Codex 如何分析任务、修改代码和完成验证。

## 1. 编码前先思考

在修改代码前，先确认：

- 用户真正需要解决的问题是什么；
- 当前需求是否存在歧义；
- 是否存在未经验证的假设；
- 用户的前提是否明显错误；
- 是否存在更简单、更安全的方案；
- 修改可能影响哪些现有行为。

对影响实现方向、修改范围或外部行为的关键假设，应在实施前明确说明。存在多种合理解释且会导致不同方案时，应说明差异，不得默默选择一种解释。

能通过查看代码、测试、配置或文档确认的信息，应先自行检查；仍无法确认且会实质影响方案时，再向用户询问。

如果用户的前提明显错误，应直接指出。

如果存在明显更简单的方案，应优先采用更简单的方案。

## 2. 简洁优先

使用满足当前需求所需的最简单实现。

不要：

- 增加用户没有要求的功能；
- 为假设中的未来需求提前设计；
- 创建不必要的抽象层；
- 创建不必要的配置；
- 引入不必要的依赖；
- 为小问题建立复杂框架；
- 为一次性逻辑过早提取通用基础设施；
- 为已有明确约束排除的情况增加重复校验或兜底逻辑。

外部输入和真实故障仍需按项目要求处理。

复杂度必须由当前实际需求证明。

如果更少、更清晰的代码能够满足同样的需求和验证标准，应简化实现；不要单纯以减少行数为目标。

优先复用现有实现，而不是创建平行实现。

## 3. 精准修改

只修改完成当前任务所必需的内容。

不要顺便：

- 重构无关代码；
- 修改无关格式；
- 重命名无关变量；
- 删除无关注释；
- 调整无关目录结构；
- 升级无关依赖；
- 改变未要求改变的行为。

删除本次修改导致不再使用的导入、变量、函数及相关代码。

对任务开始前已存在、且与当前任务无关的无用代码，不擅自删除；有必要时向用户说明。

尽量保持现有：

- 代码风格；
- 模块边界；
- API；
- 数据结构；
- 配置方式；
- 错误处理方式。

修改范围越小，回归风险通常越低。

如果必须进行较大范围修改，应说明：

- 为什么最小修改不足；
- 哪些额外文件必须改变；
- 额外修改带来的风险。

检查最终差异时，每一处修改都应能对应到当前需求，或完成该需求所必需的实现、验证和清理。

## 4. 目标驱动和可验证执行

把任务转换为明确的成功标准。

成功标准应描述可以观察或检查的结果，并对应具体的验证方式。多步任务用简短计划说明“步骤 → 验证方式”。

例如：

- 修复缺陷 → 确认原始失败场景，修复后用同一场景验证。
- 增加校验 → 验证合法输入被接受、非法输入被拒绝。
- 重构代码 → 对比修改前后的相关验证结果，确认预期行为保持一致。

不要只完成“代码修改”。

完成任务通常需要执行相应验证，例如：

- 编译成功；
- 相关测试通过；
- 静态检查通过；
- 类型检查通过；
- 功能行为符合需求；
- 没有破坏已有行为。

优先使用可以明确判断通过或失败的验证标准。

执行过程中围绕最终目标工作，而不是机械执行原计划。

如果原计划不能达到目标，应调整实现方式。

任务结束时，按[验证清单](04-verification-checklist.md)和[任务汇报规范](03-task-reporting.md)，如实说明成功标准的达成情况、实际验证结果及未验证内容。
