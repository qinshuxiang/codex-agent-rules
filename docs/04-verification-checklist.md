# Codex 验证清单

验证强度应与任务风险相称。

不要为了满足清单机械执行无关测试。

## 1. 修改范围

核对修改范围时，只将本次任务新增的差异作为本次改动审查和汇报。

只清理本次任务产生的无关改动，保留任务开始前已有的改动。

确认：

- 修改只覆盖当前任务需要的内容；
- 没有无关重构；
- 没有无关格式变化；
- 没有无关依赖升级；
- 没有意外改变公开 API 或数据结构。

## 2. 基础正确性

根据项目类型执行适用检查：

- 语法检查；
- 编译；
- 类型检查；
- lint；
- 格式检查。

只报告实际执行的项目。

## 3. 相关测试

修复 bug 时：

- 能够复现时，先确认原始失败输入或场景，修复后用同一输入或场景验证；
- 适合自动化时增加回归测试，优先确认该测试修复前失败、修复后通过；
- 无法复现时，说明已掌握的证据和缺少的验证。

不要把已有测试通过等同于该 bug 已修复。

优先执行最接近修改内容的测试：

1. 直接相关单元测试；
2. 相关模块测试；
3. 必要的集成测试；
4. 风险较高时再扩大测试范围。

不要用大量无关测试代替针对性验证。

## 4. 回归风险

检查修改是否可能影响：

- 现有接口；
- 现有配置；
- 数据兼容性；
- 错误处理；
- 权限；
- 并发；
- 性能；
- 安全边界。

只有与当前任务相关时才展开说明。

## 5. 边界情况

根据任务检查：

- 空值；
- 缺失值；
- 最小值和最大值；
- 重复执行；
- 超时；
- 网络失败；
- 权限不足；
- 非法输入；
- 并发访问；
- 部分失败。

不要无目的添加边界测试。

## 6. 文档一致性

如果行为、配置、命令或 API 改变，检查相关：

- README；
- 注释；
- 示例；
- API 文档；
- 配置说明；
- 测试说明。

文档没有受到影响时，不要为了形式修改文档。

## 7. 成功标准

任务完成前，明确回答：

- 用户要求的行为是否实现？
- 相关验证是否通过？
- 是否还有未验证内容？
- 是否存在已知风险？

## 8. 验证失败时

- 本次改动引入的失败，或当前任务相关且尚未解决的失败，应继续处理并重新验证；
- 已确认与本次任务无关的既有失败，应保留并报告，不为通过验证擅自扩大修改范围；
- 无法判断失败归因时，应说明依据与缺口，不得宣称相关验证已通过。

## 9. 无法验证时

如果受环境、权限、网络、缺少依赖或外部服务限制，无法执行某项验证：

必须说明：

- 未执行哪项验证；
- 为什么无法执行；
- 已经执行了哪些替代验证；
- 用户或后续环境如何完成最终确认。

不得把未执行写成已通过。
