# Codex 任务汇报规范

本文件规定 Codex 完成任务后的默认汇报方式。

本文件统一定义各类任务的汇报结构。结构、篇幅和汇报形式可按 `AGENTS.md` 规定，由已确认且适用于当前任务的个人偏好调整；事实、验证结果、失败和限制仍须如实说明。

## 普通任务

默认使用以下结构：

### 结论

直接说明任务状态。

示例：

`结论：登录失败问题已修复。`

### 修改

说明具体修改了：

- 哪些文件；
- 哪些函数、类或模块；
- 哪些外部行为。

不要只写“优化代码”或“修复问题”。

### 原因

说明为什么需要这些修改。

如果原因尚未完全确认，应明确标记为假设。

### 验证

列出实际执行的验证以及结果。

例如：

- `npm test`：通过；
- TypeScript 编译：通过；
- 认证相关测试：24/24 通过；
- 浏览器人工验证：未执行。

### 剩余风险

仅在存在时说明：

- 未验证内容；
- 已知限制；
- 环境问题；
- 外部依赖风险；
- 后续必要工作。

## 错误分析

默认使用：

### 问题

具体错误现象。

### 原因

已经确认的根本原因。

如果未确认，写明“假设”。

### 证据

给出日志、代码、测试或工具输出中的直接证据。

### 解决方案

说明准备进行或已经完成的修改。

### 验证

说明如何确认问题已经解决。

## 方案比较

存在多个方案时，不要只列选项。

比较：

- 核心差异；
- 实现复杂度；
- 修改范围；
- 风险；
- 依赖；
- 维护成本；
- 验证难度。

最后给出明确推荐。

推荐格式：

`推荐：方案 A。`

`原因：方案 A 修改范围最小，不引入新依赖，并满足当前需求。`

如果无法明确推荐，应说明缺少什么信息。

## 简单任务

简单任务可以用一个短段落说明，默认 2 到 4 行，但至少说明：

- 做了什么；
- 是否验证；
- 是否存在未完成内容。

## 禁止的汇报方式

避免：

- 大段叙述内部思考过程；
- 重复用户已经知道的背景；
- 用“应该没问题”代替验证；
- 用“完成”掩盖未执行测试；
- 用模糊程度词代替实际结果；
- 罗列大量低价值细节而掩盖任务状态和关键结果。
